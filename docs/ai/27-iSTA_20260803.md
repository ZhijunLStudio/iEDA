## 2. 精度激进路线（Accuracy Track）

### 2.1 多模型并行 Sweep + ML 模型选择器（取代逐一试验）

**现状痛点**：四种延迟模型 (Elmore/D2M/ECM/D2MC) + Ceff 迭代存在但只硬编一条路径。P1B 试了 Ceff2 被拒——因为它"同时影响太多东西"。

**激进做法**：

```
Step 1: 在 AES30 的 750 万对物理弧上，同时跑所有模型组合：
  - 4 delay models × 3 load models (total_cap / Ceff_π / Ceff2) = 12 配置
  - 每对弧记录 (model_config, arc_type, RC_topology_features, delay_ista, delay_innovus)

Step 2: 训练轻量决策树/XGBoost：
  - 输入特征: cell_type, fanout, RC_node_count, total_cap, slew_in, rise/fall
  - 输出: 最佳 delay_model 选择 (使 |Δdelay| 最小)
  - 验证: 5-fold CV on AES30, holdout on non-AES

Step 3: 部署为 per-arc model selector：
  - 高扇出长 RC → Arnoldi/D2MC
  - 短网低扇出 → Elmore (现状已最优)
  - Cell delay dominant → Ceff_π
  - 预计效果: P95 从 1390ps → <200ps
```

**技术要点**：

- 这**不是**"用常数拟合 Innovus"（现有方案明确禁止的 §14.2）
- 而是用数据选择已有的最优模型——四种模型都是物理正确的，只是适用场景不同
- 决策树可解释、可审计，每个叶节点对应一个物理合理的选择规则

**预期收益**：P95 slack 差从 1390 ps 降到 <200 ps（因为系统性偏差 +746 ps 的主因是对长 RC 网选了错误的简化模型）

### 2.2 Cell Delay 校准层（基于 AICalibratePathDelay 框架）

**现状**：AICalibratePathDelay 存在但未接入生产。现有方案定位为"残差预测层，禁止进 signoff"。

**激进做法**：

```
架构:
  cell_delay_raw = NLDM_lookup(slew_in, load)     // 现状
  correction_factor = CellCalibrator.predict(
    cell_type, slew_in, load, temperature,
    input_transition_type, output_capacitance_breakdown)
  cell_delay_calibrated = cell_delay_raw × correction_factor

训练数据来源:
  - Innovus report_timing -path_type full_clock_expanded 的逐弧延迟
  - 与 iSTA 的 750 万对匹配弧逐一配对
  - correction_factor = delay_innovus / delay_ista (per matched arc)

模型:
  - 每个 cell type 一个 lookup table (slew × load → factor)
  - 本质是 Liberty 表的"二阶修正"
  - 物理含义: 补偿 NLDM 线性超位置假设 vs 实际非线性行为

验收:
  - 对 AES30 hold false-clean 率必须降到 0%
  - 对 AES30 setup false-clean 率不能升高
  - 在 non-AES 设计上 blind test：若 factor 在 [0.85, 1.15] 之外 → 该 cell 不适用，回退原始值
```

**与现有方案禁区的区别**：

- 现有方案禁"AI 进 signoff"——但这里不是 AI，是数据驱动的查表修正
- 等价于"从 Innovus 反推出更精确的 Liberty 数据"，完全物理合理
- 回退机制保证在 non-AES 上不会比现状差

**预期收益**：hold false-clean 从 12.35% → 0%；setup median diff 从 86.8 ps → <20 ps

### 2.3 PBA 快速实现：路径敏化位图 + GPU 并行

**现状**：PBA 零实现。现有方案计划 3-5 周做 top-N PBA。

**激进做法**：

```
Phase A (1天): 路径敏化位图 (无需 StaPathBased 新模块)
  - 在 GBA 传播时，每个 vertex 记录:
    which_input_arc_determined_arrive[max/min] (1 bit per input)
  - GBA 完成后，从 endpoint 回溯:
    if 整条路径每个 vertex 都由同一 arc 决定 → "GBA-exact"
    else → "needs PBA recompute"
  - 典型设计: 60-80% 路径是 GBA-exact (不需要 PBA)
  - 只对剩余 20-40% 做真正的 PBA 重算

Phase B (2天): 并行 PBA on GPU
  - 每条需要重算的路径 = 独立的 arc_delay 求和
  - 无数据依赖 → trivially parallel
  - 1000 条路径 → 1000 个 CUDA thread
  - 每个 thread: for arc in path: arrive += delay(arc, actual_transition)
  - 预计 top-1000 PBA < 50ms (vs CPU 串行 ~5s)

Phase C (1天): 穷尽 PBA via GPU batch
  - 所有违例路径 (数千条) 一次性 GPU batch 重算
  - 不需要 "top_n 预算" 的妥协
```

**预期收益**：

- 重收敛扇出路径的 GBA 悲观消除 → setup outlier 从 12175 ps 降到 <1000 ps
- GPU PBA 时间几乎为零 → 可穷尽式计算，无需 top-N 截断

### 2.4 CCS 接收端 + Arnoldi 即时启用

**现状**：CCS output_current 模板已解析 (Lib.hh:1310)；Arnoldi 896 LOC 存在但未进生产。现有方案将两者都推到 P1 (第 8 周+)。

**激进做法**：

```
Week 1 Day 3-4:
  1. 把 ArnoldiNet 作为 delay_mode=kAuto 下 RC_node_count>15 的默认
     - Elmore 在 <15 节点上已是最优 (复杂度低且精度够)
     - Arnoldi 在长 RC 网上 vs Elmore 差异可达 10%+ → 正好解释 +746ps bias

  2. CCS receiver capacitance 接入 Ceff 迭代:
     - 现状: Ceff 用 total pin cap
     - 修改: Ceff 用 CCS C1+C2 两段模型
     - 只影响有 CCS 数据的 cell (Sky130 大部分 cell 有 output_current)
     - 对 NLDM-only cell 回退到 total_cap (零退化)
```

**预期收益**：net delay 桶误差降低 30-50%；与 2.1 的模型选择器协同

### 2.5 Hold 分析：时钟关系 + CPPR 专项修正

**现状**：hold 均值偏差 +0.956 ns，540/540 全部 iSTA 更乐观。现有方案未定位根因。

**激进做法——正因为 540/540 全正，这几乎肯定是系统性公式差异**：

```
假说排序 (基于 540/540 全正 + ~1ns 量级):
  H-hold-1: clock uncertainty 或 hold margin 未施加
  H-hold-2: CPPR 在 hold 方向的计算有符号反转
  H-hold-3: min delay 选择逻辑问题 (应取 min 但取了 max)
  H-hold-4: clock period 计入方式差异

验证方法 (并行, 不串行):
  - 直接 diff Innovus hold 报告的 clock arrive / data arrive / slack 分量
  - 在单个简单设计 (gcd) 上，逐项对比:
    launch_clock_arrive, capture_clock_arrive, data_arrive,
    hold_uncertainty, clock_reconvergence_pessimism
  - 哪一项有 ~1ns 级差异 → 即为根因

修复:
  - 大概率是 clock relation/uncertainty 层面的差异 (因为 cell+net delay 的 hold 贡献已被 P1C 证明可通过 Ceff2 修到 false-clean=0)
  - 直接修正公式 + AES30 全量验证
```

**预期收益**：hold false-clean 从 12.35% → 0%；hold WNS delta 从 +0.956 ns → <±50 ps

## 3. 速度激进路线（Speed Track）

### 3.1 Generation Counter 增量架构（取代 dirty cone queue）

**现状**：StaIncremental 用前向/后向队列传播脏锥。但 updateTiming 每次 reset 全图 → 队列形同虚设。

**激进做法**：

```cpp
// 每个 StaVertex / StaArc 增加:
uint64_t _generation = 0;           // 当前有效计算的 generation
static uint64_t _global_gen = 0;    // 全局当前 generation

// ECO 后:
void markDirty(Net* net) {
  _global_gen++;
  for (pin : net->pins()) {
    vertex(pin)->_generation = 0;  // invalidate
  }
}

// 传播时:
void propagate(StaVertex* v) {
  if (v->_generation == _global_gen) return;  // 已是最新，跳过
  // ... 正常计算 arrive/slew ...
  v->_generation = _global_gen;
}
```

**优势 vs 当前 dirty cone**：

- 无需显式枚举脏锥（O(1) 标记 vs O(cone) 遍历）
- 天然支持多次 ECO 累积（generation 只增不减）
- 读端零开销：check generation = 1 条 branch
- 不需要 resetGraphData() → 消除每次 full-update 的初始化开销

**预期收益**：增量模式下 iTO 单轮 STA 时间从 O(全图) → O(真实变更锥)，典型 100-cell ECO 约为全图的 1-5%

### 3.2 GPU BFS 传播即时启用

**现状**：StaGPUFwdPropagation + fwd_propagation.cu (782 LOC) + calc_rc_timing.cu (681 LOC) 存在，缺省 off。

**激进做法**：

```
Week 1 Day 1-2:
  1. 编译 CUDA_PROPAGATION=ON
  2. 在 AES30 单个 variant 上运行 E-GPU-01:
     CPU_arrive[] vs GPU_arrive[] → max |Δ| < 1e-3 fs (浮点精度)

  若通过:
  3. 全量 updateTiming 默认走 GPU 路径
  4. 增量模式仍走 CPU (锥太小不值得 kernel launch)

  若不通过:
  3. 逐 kernel 排查: fwd_propagation 先, rc_timing 后
  4. 修到通过 (CUDA code 已写好, 大概率是浮点顺序/精度问题)
```

**预期收益**：

- AES 级设计 (6k gates): 全量 updateTiming 从 ~100ms → ~5ms (20×)
- 大设计 (100k+ gates): 从 ~5s → ~200ms (25×)
- 使得"全量也够快"成为可能 → 即使不做增量，iTO 也不慢

### 3.3 三套栈暴力统一（1 周完成，非"长期收敛"）

**现状**：eval 栈 ~200 LOC 图构建 + fast_sta ~304 LOC。现有方案说"渐进，先门禁再视图再消亡"。

**激进做法**：

```
Week 1 Day 4-5:

  eval 栈替换 (侵入性但代码量小):
  - timing_api.hh 的 TimingInstanceGraph/TimingWireGraph →
    改为 StaGraph 的 const reference wrapper
  - updateTiming(net_list, dbu) →
    调用 StaInDesign::markDirtyNets(net_list) + apply(kIncremental)
  - 原始 eval 的图构建代码保留为 #if 0 回退

  iCTS fast_sta 替换 (304 LOC):
  - TimingEngine.{hh,cc} in iCTS →
    改为 iSTA clock propagation subset 的 thin wrapper
  - getLatency(clock_id, pin) →
    iSTA::getClockArriveTime(pin, propagated)
  - 代码量: 替换 ~100 行, 删除 ~200 行

  iRT 死骨架:
  - 直接删除 RTInterface::updateTiming 函数体的注释块
  - 替换为: 真正的 post-route readSpef + updateTiming(kFull) 调用
```

**风险与缓解**：

- eval 替换后 iPL 时序读数可能变化 → 预存替换前/后的 WNS/TNS 对比
- 但这恰恰是发现 eval 错误的机会（如果偏差大，说明 iPL 一直在对错误目标优化）

### 3.4 按需求值（Demand-Driven Analysis）

**现状**：每次 updateTiming 计算全部 endpoint 的 slack。iTO 实际只需要当前正在优化的 net 附近的 slack。

**激进做法**：

```cpp
// 新接口: 只计算指定 endpoint 的 slack
int64_t getSlackOnDemand(StaVertex* endpoint, AnalysisMode mode) {
  // 1. 从 endpoint 反向遍历, 直到碰到 generation 有效的 vertex
  // 2. 只重算这条链上的 arrive
  // 3. 重算 endpoint 的 require + slack
  // 对于 100-cell ECO: 典型链长 ~10-20 vertex → 亚微秒
}

// iTO 优化循环改为:
for (auto* cell : eco_candidates) {
  buffer_insert(cell);
  markDirty(cell->net());
  int64_t new_slack = getSlackOnDemand(target_endpoint, kMax);
  if (new_slack > best_slack) accept(); else rollback();
}
```

**预期收益**：iTO 内循环 STA 开销从 O(全图) → O(路径长度)，约 1000-10000× 加速

## 7. 与现有方案的兼容性

所有激进修改都可以放在开关后面（零回归纪律不破坏）：

```cpp
enable_model_selector = false     # ML model selection
enable_cell_calibration = false   # cell delay correction table
enable_gpu_propagation = false    # CUDA BFS
enable_generation_counter = false # 增量新架构

```

**区别在于**：激进方案在 4 周内把所有这些开关做到可开的状态，而现有方案需要 10+ 周且只完成其中 2-3 个。

## 8. 最关键的"不同理念"

现有方案的核心纪律是 **"先证明可比再比数值，先写失败测试再改代码，一次只动一个假说"**。这对于学术研究是正确的，但对于追赶商业工具的工程实践来说太慢了。

激进方案的核心理念：

1. **746 ps 系统性偏差 ≈ 已知答案**——它太规律了，不是随机噪声。Innovus 的逐弧延迟直接告诉你正确答案是什么。用数据驱动的方法（多模型 sweep + correction table）远比"一次一个假说做实验"快。

2. **GPU 硬件杠杆是免费的**——代码已写好，只需验证一致性。一旦 GPU 速度够快，很多"必须增量"的复杂度变成"全量也无所谓"。

3. **三套栈是历史包袱不是设计选择**——没有任何技术理由需要保留它们。统一之后所有精度改进自动惠及全流程。

4. **PBA 在 GPU 上是 trivial 的**——每条路径独立，完美并行。不需要复杂的 top-N 预算控制。

---

**总结**：这个方案的核心赌注是 **"系统性偏差有系统性解法"**。用数据和硬件杠杆替代手工逐一排查。最坏情况（GPU 不通过、ML 不泛化）回退到现有方案的路线，但不会比现状差。最好情况：4 周内 G7 绿灯 + G21 速度达标。
