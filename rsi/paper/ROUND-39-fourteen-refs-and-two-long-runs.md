## 2. Two measurements are in flight and are slow for a structural reason

**The congestion re-check.** The first re-test of an excluded mechanism is congestion-aware global
placement (-congestion_effort 4), re-tested because every exclusion was established before the protocol
fixes. Its first row is in: s38584_ics55_a at effort 0 gives 0.9695 / 1.1656 / 1.6, **identical to the
standing measurement of the same configuration**, which is a useful internal consistency check on the
whole pipeline.

Effort 4 is slow because it calls the congestion evaluator inside the Nesterov loop, so a single design
takes tens of minutes instead of one. That is a fact about the mechanism worth recording on its own: if
it is adopted, its cost is not the two extra evaluator calls of the SR-11 guard but something much
larger.

**The aggregate.** Fifteen designs times two arms, each requiring a trial-route evaluation, with the
large designs taking minutes per evaluation.

Neither is stuck - both are spending CPU - but neither will finish inside this round.

## 5. Note on what is deliberately not reported

The aggregate currently on disk is an older one written while its process was started with a CPU set
outside the machine's range (600-663 against 512 cores), which made every congestion measurement fail and
left the ratios as wirelength only. Those numbers are not reported. The running aggregate uses a valid
CPU set.

That is the second time in this campaign that a harness-run parameter silently invalidated a batch - the
first was the arm-switching defect of round 36. Both were caught by a value that looked wrong rather than
by a check, which is the argument for the consistency check used in section 2: measuring a configuration
that is already known, and seeing whether it reproduces.
