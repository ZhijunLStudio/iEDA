# iEDA 自我改进系统（RSI）工作梳理

> 目的：把「读评测结果 → 定位缺陷 → 改 iEDA 源码 → 标准全流程复测 → 归因 → 再找下一个缺陷」这个闭环
> 说明清楚：系统怎么搭的、改了哪些代码、为什么这么改、拿到了什么结果、以及哪些还没做到。
> 所有数字来自同一批测量产物，可按需复算；未达成项与失败项均如实列出。

---

## 一、摘要

我们搭了一套**以「验证器保真度」为核心的自我改进系统**，在真实 EDA 全流程（gp→lg→dp）上
对 iEDA 源码做算法层修改，并用**同一把尺子**衡量「原版 iEDA / 改后 iEDA / Innovus」三方。

**拿到了什么：**

- 定位到 iEDA 的一个**具体算法缺陷**：详细布局（DP）的换位循环**只按线长接受移动**，
  对拥塞无感知；而流程给路由器的布局，就是**一遍合法化 + 一遍详细布局**的产物 ——
  **流程里根本没有让 LG+DP 收敛的循环**。
- 据此做了三处源码改动（SR-10 / SR-11 / SR-21），**全部改动都落在流程真正会执行到的调用点上**。
- **实测效果是单向交易**：拥塞明显改善（总溢出 8/13 变好、峰值 9/13 变好，平均收窄约 16%），
  **代价是线长（10/15 变差）与时序（3 个设计变差）**。
  方向是对的 —— 因为**拥塞正是我们唯一系统性失分的维度**。
- **全维度通过的设计数：原版 3/15 → 改后 4/15 →（含 SR-21 已测设计）5/15。**

**没做到什么（同样重要）：**

- **尚未实现「全维度超越 Innovus」**。拥塞仍是唯一系统性失分维度（union 失 8/13、峰值失 8/13），
  本次改动**只是收窄了 16%，没有解决它**。
- 有两处**真实的自伤**必须记在账上：`gcd_sky130_a` 三项全变差；`s1238` 从「时序无违例」掉入「有违例」。
- 时序维度：**7 个 sky130 设计里 6 个已胜**，唯一贴线输的是 `aes` 的 TNS（1.003，差 0.26%）。
- 15 个设计中，**7 个无时序数据**（nangate45 在 STA 内崩溃、ics55 读 LEF 中断），
  因此**「五维全胜」只能在 sky130 上判定**。

## 二、系统是怎么搭的

### 2.1 闭环

```
  ┌──────────────────────────────────────────────────────────────┐
  │  1. 用标准全流程跑 gp → lg → dp（不带 agent、不做候选搜索）        │
  │  2. 同一把尺子量「我方 / Innovus」两侧（合法化后、同一评测器）        │
  │  3. 读结果 → 定位 iEDA 的**具体**缺陷                            │
  │  4. 改 iEDA 源码（算法/方法层）                                  │
  │  5. 回到 1，复测；归因到这次改动                                   │
  └──────────────────────────────────────────────────────────────┘
```

**编排是机械执行**：跑流程、跑评测器、落盘，不做候选挑选、不做搜索；
**一切改进只能来自源码修改**。这条边界是刻意的 —— 否则「改进」会退化成「调参」或「挑结果」。

### 2.2 目录结构

```
ieda/rsi/
├── protocol/    预注册协议 v1.0 + 7 份修正案（各带 sha256 冻结）
├── harness/     ~100 个脚本：编排、评测、A/B、归因、专项目检
├── analysis/    分析产物（锚点、诊断、对照表）
└── paper/       65 份逐轮记录 + 草稿 + 机制说明
```

### 2.3 评测阶梯（验证器分级）

协议里把「验证器强度」定义成一条成本阶梯，**每一级都可执行、可复算**：

| 级别 | 信号 | 成本量级 |
|---|---|---|
| V0 | 布局器内部自报溢出 / 未合法化线长 | 秒 |
| V1 | GP+LG+DP 结果的 DEF 线长 | 十秒 |
| V2 | V1 + iRT 试布线 EGR（总溢出 / 峰值） | 分钟 |
| V3 | V2 + iSTA（WNS / TNS / hold / freq） | 十分钟 |
| V4 | V3 + 全流程到 GDS 与 DRC | 小时 |

**本次工作把验证器从 V1 抬到 V2+V3** —— 这是后面一切结论能站住的前提：
拥塞与时序都是**流程自带评测器**给出的，不是我另写的代理指标。

### 2.4 七个方法硬约束（防止自欺）

这些不是形式，每一条都对应一次踩过的坑：

1. **结论必须多种子（≥3）同种子配对** —— 单设计种子波动实测峰值差达 67%。
2. **源码比较的两个二进制必须同提交构建、只差被测改动；比较前先列清每个二进制里有什么**
   —— 曾因对照选错，把守卫的功劳记到了另一个改动上。
3. **只在网表严格匹配的设计上下结论** —— 24 个 sky130 参考 DEF 里有 17 个是不同网表。
4. **禁止看 GP 阶段数字下结论** —— pre-LG 与 post-LG+DP 的线长相关系数 ρ = **−0.891**（负相关！）。
5. **不把配置差、噪声、候选挑选当算法改进。**
6. **每次改动须有：改了什么、对应哪个实测缺陷、多种子效果、不达标时如实结论；失败必须撤回并写明原因。**
7. **相信叙述前先读 diff** —— 无副作用的改动（仪表/注释）只能被 diff 看见。

## 三、改了哪些代码、为什么

改动共 **10 个文件、+338 / −12 行**（相对本战役起点），其中**实质性算法改动只有三处**，
全部在 `src/operation/iPL/`（布局器）内。

### 3.1 定位到的缺陷

**计数器给出的关键事实**：统计每个 iEDA 进程的 `Start Detail Placement` 次数 ——

| | 详细布局调用次数 |
|---|---|
| **标准流程（原版）** | **1** |
| 对照实验 | 3 |

**也就是说：流程只做一遍合法化 + 一遍详细布局就交棒给路由器。**
**它把「一遍」当成了「收敛」** —— 这是个流程约定，不是一个判据。

### 3.2 SR-10 —— 在详细布局前后调用项目自带的拥塞评测器

- **改了什么**：在 `PLAPI` 中，于详细布局前后调用流程自带的拥塞评测
  （`notifyPLCongestionInfo` → 试布线 EGR），拿到**总溢出 union 与峰值 max**。
- **为什么**：DP 的换位循环**只按线长接受移动**，对拥塞完全无感知。
  要能对 DP 的结果做判断，先得**在流程内**拿到拥塞数 —— 这是把验证器从 V1 抬到 V2 的最小改动。

### 3.3 SR-11 —— 支配性守卫：DP 变差就回退

```
若 （DP 后峰值变差） 且 （DP 后总溢出未改善）：
    回退到合法化结果
```
- **改了什么**：在 `PLAPI::runDP` 内加这个守卫。
- **为什么**：DP 的接受判据（线长）与我们要优化的目标（拥塞）**不一致**，
  于是 DP 会把布局改得拥塞更差。守卫是**Pareto 安全网**：只在确凿变差时回退。
- **实测特性**：约 **1/3** 的种子对上触发，其余情形**逐字节不变** ——
  它是安全网，**不提升均值**。

### 3.4 SR-21 —— 让 LG+DP 多跑几遍，保留最好的一遍

- **改了什么**：新增 `PLAPI::runGatedFinish(max_extra_passes)`，从
  **`PlacerIO::runDetailPlacement()`** 调用（即 `placer_run_dp` 命令**真正落到**的函数）。
  最多跑 2 遍额外 LG+DP，每遍后记录**整个布局状态**与两个拥塞数，
  最后**回退到最好的一遍**（「好」= 峰值优先、总溢出次之，与评估口径一致）。
- **为什么**：先做了**无门控**的多遍历实验，发现效果很大但**轨迹非单调**：

| 遍历 | 峰值 | 总溢出 |
|---|---|---|
| 1（出厂） | 3 | 37 |
| 2 | **6**（变差） | 27 |
| 3 | **2**（最好） | **16** |

  **峰值先变差、后变好。** 所以任何「每步都必须不变差」的规则都会**拒绝第 2 遍**——
  而第 3 遍的收益正是从第 2 遍来的。**这就是必须「记录最好一遍」而不是「逐步守门」的原因。**

### 3.5 三处改动的共同点：**落在流程真正会执行的位置**

这一点花了四轮才学明白，且**每次失败都记录在案**：

| 尝试 | 结局 | 教训 |
|---|---|---|
| SR-15 | 撤回 —— 错放的 `continue` 毁掉一个收敛中的设计 | 不要跳过循环体 |
| SR-17 | 撤回 —— 该跑 4 遍，实跑 **62 遍** | 必须限界 + 每遍记录 |
| SR-18 | 撤回 —— **从未执行**（放进了流程不调用的函数）| 放在流程会跑的位置 |
| SR-19 | 撤回 —— **从未执行**（同上）| 同上 |
| **SR-21** | **执行、有界、自主决策、有实测效果** | 以上全部 |

流程发出的是三条独立 Tcl 命令（`placer_run_gp` / `placer_run_lg` / `placer_run_dp`），
各自映射到独立 API，**不经过任何复合入口**。核实后的落点：

```
placer_run_dp  →  CmdPlacerRunDP::exec()  →  PlacerIO::runDetailPlacement()  →  PLAPI::runDP()
```

SR-21 目前只完整测了 3 个设计，**但其中一个的结果是本次工作最好的**：

| 设计 | 维度 | 无 SR-21 | **有 SR-21** | 结果 |
|---|---|---|---|---|
| **gcd_ics55_a** | 总溢出 | 1.85（失分）| **0.80（通过）** | **失分 → 全通过** |
| | 峰值 | 0.50 | **0.33** | 改善 |

**`s1238_sky130_a` 是门控有效的最强证据**：它产出的布局与出厂流程**逐字节相同** ——
因为它识别出额外遍历会同时恶化两个拥塞数，于是**一个字节都没改**。

**代价**：每遍额外遍历 = 1 次合法化 + 1 次详细布局 + 2 次试布线评测，实测**约 6 分钟/遍**；
用满 2 遍约 3 倍后置时间。**这是自觉的取舍，不是免费的改进。**

## 五、撤回的改动（诚实记录）

本战役共**撤回 16 个改动**，**每个都有实测理由，均不在代码树中**：

SR-2 / SR-3 / SR-4 / SR-5 / SR-7 / SR-8 / SR-9 / SR-12 / SR-13 / SR-14 / SR-15 /
SR-16 / SR-17 / SR-18 / SR-19 / SR-20。

它们分两类：

- **调参型**（密度罚项强度、`max_phi_coef`、迭代预算、网格、拥塞感知线长档位、方向系数）：
  实测**符号随设计变化**，不能作为默认值。
- **实现有缺陷型**（SR-15 / SR-17 / SR-18 / SR-19）：**想法对、实现错**，
  且**在源码里看不出来，只能在行为里显形**。

**这 16 份撤回记录本身是系统的产出**：它们把「什么不起作用」变成了可复用的负知识。
