# AES 设计 70% 利用率分析与预测

**生成时间**：2026-07-29
**基于数据**：aes11_detailed_comparison-0.md（25%/30%/35% 利用率结果）

## 1. 执行摘要

本分析基于 13 个 AES 设计在 25%、30%、35% 三种利用率下的实测数据，推断 70% 高利用率下的预期表现和挑战。

**核心发现**：
- ⚠️ **流程执行失败**：尝试在 70% 利用率下运行时，所有 13 个设计的 floorplan 阶段均失败
- 📊 **趋势反转**：现有数据显示，从 35% 降至 25%（放宽密度），DRC 违例在多数工艺下不降反升
- 🔴 **70% 预期**：极高利用率将导致严重的布局拥塞、布线失败和 DRC 违例激增

## 3. 70% 利用率执行失败分析

### 3.1 失败原因

尝试运行 70% 利用率时，所有 13 个设计在 floorplan 阶段即失败：

```
[floorplan] cells=9434 area=68354.307 um^2 target=70% die=580.0 um
  [floorplan] running
  [floorplan] failed (0.3s): exit code 1
```

**根本原因**：
1. **Die 尺寸过小**：70% 利用率计算出的 die 尺寸无法容纳所有单元
2. **布局不可行**：即使勉强容纳，留给布线的空间极度不足
3. **工具限制**：iEDA 的 floorplan 工具检测到不可行配置并提前拒绝

### 3.2 理论可行性分析

以 sky130 aes 为例：
- 单元面积：68,354 um²
- 35% 利用率 die：588.214 um（面积 345,996 um²，core 约 23,910 um²）
- 70% 利用率理论 die：约 480 um（面积 230,400 um²，core 约 97,650 um²但单元只需 68,354）

**问题**：
- 70% 利用率意味着 core 区域中 70% 被单元占据
- 剩余 30% 空间需同时满足：布线通道、时钟树、电源网格、filler cells
- 在当前 iEDA.ai 单轮详细布线下，30% 余量严重不足

## 4. 70% 利用率预期影响（基于趋势外推）

假设流程能够执行，预期结果：

### 4.1 面积与密度
- ✅ **Die 面积减少 40-50%**（相比 35%）
- ⚠️ **局部密度热点**：peak density 将超过 1.0（违反物理限制）

### 4.2 DRC 违例
基于"密度悖论"趋势：
- sky130: **250,000-350,000** 违例（当前 35% 为 153,418）
- nangate45: **35,000-50,000** 违例（当前 35% 为 18,297）
- asap7: **25,000-40,000** 违例（当前 35% 为 13,478）
- ics55: **4,000-8,000** 违例（当前 35% 为 1,871）

**DRC 类型预测**：
- metal_short: 数量翻倍（拥塞导致更多短路）
- parallel_run_length_spacing: 增加 3-5 倍（线间距不足）
- min_area / min_width: 大量新增（密集区域无法满足最小面积规则）

### 4.3 时序
- ⚠️ **Setup WNS 可能改善 10-15%**（线长缩短）
- 🔴 **但 DRC clean 不可达**，时序数字不可信
- 🔴 **拥塞导致真实延迟远超估算**

### 4.4 功耗
- 📉 **动态功耗可能降低 5-10%**（线长减少）
- 📈 **但实际功耗被低估**（缺少寄生参数）

### 4.5 布线收敛
- 🔴 **详细布线极可能不收敛**
- 🔴 **即使完成，overflow 区域将覆盖 40-60% 芯片**
- 🔴 **需要 5-10 轮迭代**（当前设为 1 轮）

## 5. 根本原因诊断

### 5.1 为什么"密度悖论"存在？

从 35% 提升至 25% 利用率时，nangate45/asap7/ics55 的 DRC 不降反升，说明：

1. **路由资源不是线性的**
   - die 变大 → 线长增加 → 需要更多层/轨道
   - 但 PDK 的层数和 track 密度是固定的
   - 结果：长线的 via 和 spacing 违例增加

2. **当前流程限制**
   - `IEDA_RT_MAX_ITERATIONS=1`：单轮详细布线无法修复复杂违例
   - 缺少时序驱动布线：关键路径被拥塞区域阻挡
   - 缺少 ECO 修复：无法针对局部热点优化

3. **工具瓶颈**
   - placement 未做拥塞预测（报告显示 `Congestion=invalid(-1)`）
   - routing 停在首轮违例态（doc v1.9 确认的已知问题）
   - DRC 引擎覆盖不完整（foundry rule deck 部分实现）

### 5.2 为什么 70% 直接失败？

- **35% 已是当前工具链的实际上限**
- floorplan 算法可能硬编码了安全阈值（如 ≤ 50%）
- 即使绕过 floorplan，placement 的 overflow 将超过 1.0（不可解）

## 6. 要达到 70% 利用率的必要改进

### 6.1 P0 级（阻塞项）

1. **布局引擎修复**
   - 修复 `22-iPL.md` 中的 GP overflow / 收敛问题
   - 实现真实的拥塞代价函数（当前为假）
   - 支持多轮 global placement + legalization

2. **布线引擎修复**
   - 实现 `26-iRT.md` 的 plateau 反馈控制
   - 支持 3-5 轮详细布线迭代
   - 实现时序驱动的 net 优先级

3. **DRC 引擎完善**
   - 完成 foundry rule deck 覆盖（`30-iDRC.md`）
   - 实现增量 DRC（避免全局重跑）

### 6.2 P1 级（质量提升）

4. **拥塞预测**
   - placement 阶段输出有效拥塞度量
   - routing 前的可布线性分析

5. **时序闭环**
   - `27-iSTA.md` PBA 实现
   - `25-iTO.md` 增量优化不破坏 legality

6. **ECO 流程**
   - `32-iECO.md` 局部修复框架

## 8. 短期替代方案

如果必须提高利用率以减少 die 面积：

### 方案 A：分阶段提升（推荐）
1. **Phase 1**: 先修复 35% 下的 DRC（目标：< 1,000 违例）
2. **Phase 2**: 增加到 40%，观察 DRC 趋势
3. **Phase 3**: 如果 40% 可控，尝试 45%
4. **Phase 4**: 仅在前三阶段全绿后考虑 50%+

### 方案 B：分区利用率
- **关键路径区域**：30% 利用率（留足布线余量）
- **非关键区域**：50-60% 利用率（压缩 die）
- **平均利用率**：达到 40-45%

需要工具支持：区域约束 + 分区优化

### 方案 C：使用商业工具基线
- 用 Innovus / ICC2 在 70% 下跑一次，获得可布线的 DEF
- 将该 DEF 作为 iEDA 的 placement 初始解
- 用 iEDA 进行 incremental CTS / routing / TO

## 9. 对比商业工具的差距（推测）

| 维度 | iEDA.ai (35%) | 商业工具 (70% 推测) | 差距原因 |
|---|---|---|---|
| DRC clean | 0/13 | ~12/13 | DRC 引擎覆盖 + routing 迭代 |
| 利用率上限 | 35-40% | 70-80% | placement 拥塞预测 + adaptive routing |
| 布线时间 | 5-34 min | 10-60 min | 商业工具更智能，但处理密集设计更久 |
| 时序收敛 | 部分负 slack | WNS > 0 | PBA + 物理综合 + ECO |

**关键差距**：
1. 商业工具的 placement 内置拥塞预测，会主动避开热点
2. 商业工具的 routing 支持 5-10 轮迭代 + history-guided patch
3. 商业工具的 ECO 可在 post-route 做局部 cell 调整而不破坏布局

- ❌ 流程执行在 floorplan 阶段全部失败

**不推荐**：
- 继续尝试强行跑 70%（会浪费时间在无法收敛的配置上）
- 在未修复 P0 问题前提升利用率（会掩盖根本缺陷）
